# Mori 数字员工调度（带选人门禁）

把任务交给 Mori 平台的数字员工（Employee）执行。**默认流程必须先让用户选员工**，再派发；当前调用方（Codex、Kimi、Claude 等）负责选人、会话管理与结果汇报，真实执行由员工绑定的 T3/Codex 实例完成。

## 0. 验证真实调用通道与身份

“工具目录”是客户端展示的可调用操作清单，并不是 Mori 是否可用的判断依据。下文的 `mori.*` 表示平台操作；可通过任一已验证通道执行这些操作：

1. **客户端 MCP 工具**：已有 `mori.whoami`、`mori.list_employees` 等工具时直接调用，工具名可能带 `mcp__` 前缀。
2. **真实 MCP 适配器**：有执行工具、已安装的 Mori stdio 适配器和账号配置时，可以启动适配器，按 MCP 协议调用 `initialize`、`tools/list`、`tools/call`。不要求先把工具注册到客户端清单，也不要求为了脚本调用重启客户端。
3. **已授权 HTTP API**：可使用 Mori HTTP 客户端调用真实 `/api/v1` 接口，保留平台账号登录、Cookie、CSRF、幂等键及服务端权限校验。操作映射与等待规则见 [references/transports.md](references/transports.md)。直接 API 请求同样必须遵守后文选人、审批与取消流程。

使用会话里已经授权的地址、凭据与调用能力；先检查现有配置并做只读连通验证。配置示例在 Mori 仓库 `mcp/main.ts` 头部（聚合仓库位置为 `projects/mori/mcp/main.ts`）。`MORI_BASE_URL` 要保留部署子路径；`MORI_USERNAME`、`MORI_PASSWORD` 从已配置环境/密钥绑定读取，不把密码、Cookie 或 CSRF token 输出到聊天、日志或提交文件。

在选人前，必须通过实际响应确认当前账号身份和可见员工。地址存在、适配器文件存在、`tools/list` 成功或登录页返回 200，都不能证明账号已认证或有员工执行权限。只读探测不得创建员工、建会话或发任务。

某通道不可用时，检查其余**已授权且实际可用**的通道；不因客户端缺少注册工具直接停工。全部通道不可达、身份认证失败、所需权限不足，或无法确认接口契约时，才停止对应操作并报告具体地址、阶段、错误码和缺失配置。不得通过其他路径绕过网络策略、TLS 校验或平台权限。

真实脚本/MCP/API 请求是有效派发通道；本地 Agent 或 Blueprint 本身不能冒充 Mori 数字员工。派发结果必须关联平台实际返回的 employeeId、conversationId 与 turnId，不得编造记录。

## 1. 选人门禁（强制，每次派发前）

1. 执行 `mori.whoami` 与 `mori.list_employees` 对应操作，确认实际账号并取可见员工。HTTP 方式使用会话与员工 API；身份字段或员工字段未返回时标记“未提供”，不得猜测。
2. 把结果渲染成**编号列表**交给用户选择，每位员工一行，至少包含：`编号｜名称｜角色/类型｜模型｜运行时状态｜节点｜暂停/归档标记`。列表末尾写清选择方式：「回复编号或名称」。
3. **跳过选人提示的唯一情形**：用户在当次请求里已经明确点名了某名员工（名称或 ID 可唯一匹配）。模糊匹配到多名时仍要列出候选让用户确认，不得自行替用户决定。
4. 用户说「随便/你决定/最快的」时：从状态 `ready`、未暂停、未归档的员工中任选一名，并在派发前明说「按你的授权我选择：X（理由：就绪且未暂停）」。
5. 不可选：已归档（archivedAt 非空）、已暂停（paused）、运行时非 ready 的员工。列表中标注原因；若全部不可用，停止并报告，不要强行派发。
6. 同一时刻一名员工只能跑一个任务。选人后、建会话前，若 `mori.get_runtime`（需要先建会话则无此项检查）或平台返回忙/占用错误，向用户说明并建议换人或等待，不要排队硬塞。

## 2. 派发执行

1. `mori.create_conversation`（employeeId = 用户选定的员工，title 用任务一句话概括）→ 记录 conversationId。
2. `mori.send_message`：`wait=true`，timeoutSeconds 默认 120，最长 600。把用户原任务忠实转述（不要替用户加需求），`interactionMode` 用 `default`（用户明确要求先出方案时用 `plan`）。
3. **待处理交互必须带回给用户**：若返回（或后续 `mori.get_runtime` 显示）`awaiting_approval` / `awaiting_input`，把交互内容原文呈现——审批给出可选 decision 及含义，补充提问逐条列出——等用户答复后用 `mori.respond` 继续；可循环多轮。审批决定永远由用户给，Kimi Work 不得代批。
4. **RECONCILIATION_REQUIRED 自助结算**：若 `mori.send_message` 返回 `RECONCILIATION_REQUIRED`（409），说明该员工有一笔结果未知的任务阻塞派发，错误 `details.turnId` 即阻塞任务。R30 起直接用 `mori.reconcile_turn`（turnId = details.turnId）向 T3 核对真实终态并结算，结算成功后重发消息；不要反复重发，也不要改用 stop_turn/wait_turn 硬试（它们不能结算历史遗留任务）。
5. **向刚被取消任务的会话重发是大坑**：旧会话的 T3 thread 可能仍被上一笔任务的审批占用（新任务创建即转 needs_reconciliation：「approval_required: 已绑定会话仍在等待处理」），且运行时快照停留在旧任务终态会误导等待结果。任务被取消后要重发时，**优先建新会话派发**；已产生的 needs_reconciliation 用 `mori.reconcile_turn` 结算（R30 补丁起连「从未下发到 T3」的任务也能自动结算）。
6. 完成后用 `mori.get_runtime` 取产出文件与最终状态；需要全文时再用 `mori.get_messages`。

## 3. 汇报

- 开头一行结论：哪个员工、做了什么、结果状态。
- 员工回复正文（长则摘要 + 关键结论），产出文件给路径/文件名并说明如何取。
- 成本与边界：实际调用通道、本次等待轮数、交互轮数；员工模型仅引用平台返回字段，区分配置模型与已核实的实际执行模型，未返回时写“未提供”。
- 失败时给出平台返回的 error code/message 原文摘要与下一步建议（重发 / 换人 / 停止：`mori.stop_turn`）。

## 4. 纪律

- 选人列表必须与 `list_employees` 返回一致，不得编造员工或状态。
- 用户取消时：若任务在跑或有待交互，先 `mori.stop_turn`（带 expectedTurnId）再汇报已停止。
- 不在对话中粘贴平台返回的原始大段 JSON；摘要呈现，原文落盘仅在用户要求时。
- 本 Skill 只负责调度与交互，不修改员工类型、Skill 绑定或平台配置。
- 安装 Skill、接入 MCP、平台受理任务、员工完成任务、生产上线是不同状态；分别按实际证据汇报。技能更新任务须区分仓库源文件、平台私有能力库、类型固化版本与员工磁盘副本，不能用源码更新推断线上副本已更新。
